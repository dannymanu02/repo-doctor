# Evaluation runner

## Install into your existing project

Copy `evaluate.py` and `eval_cases.py` from this archive into the same folder as
`doctor.py`. Keep your current working app, prompts, model settings, and demo.
The runner uses the version 0.3 functions including your completed-response EOF
parser adjustment. The archive's `doctor.py` includes that adjustment if needed.
No extra package is required. Keep Ollama open.

In Terminal, from your project folder:

```bash
source .venv/bin/activate
python evaluate.py --self-check
python evaluate.py
```

The first command checks all buggy fixtures and their reference fixes without
calling the model. It should print six `fixture_verified` outcomes. The second
runs six new cases against `qwen3:1.7b`. It makes two sequential calls per case
unless diagnosis fails. Based on your previous 17–32 second runs, allow several
minutes, though times may differ. There are no automatic retries.

The app need not be running. Avoid clicking Diagnose during evaluation so both
workloads do not compete for memory and inference capacity.

For one case:

```bash
python evaluate.py --case inclusive_range
```

A later comparison can use `--model MODEL_NAME` after downloading that model.
Keep the case set and prompts fixed during a comparison. Repeated runs may vary;
this is a small development benchmark, not a claim about production accuracy.

## What it measures

Six fresh synthetic examples cover inclusive boundaries, numeric strings,
numeric sorting, stable deduplication, timeout unit conversion, and normalized
configuration lookup. The last two have a separate config file.

Each case gets a brand-new temporary repository. Before model calls, the runner
checks that the buggy code fails predefined assertions and its reference repair
passes, then restores the original code. Only original source, README, issue,
and the first model diagnosis enter inference. Neither reference fixes nor test
assertions are included in the model-visible repository.

After an edit passes Repo Doctor's checks, the runner writes that edit only to
the temporary fixture and runs trusted predefined tests against it. Tests are
not generated by the model. Your demo and other repositories are never patched.
Python bytecode writing is disabled to avoid reusing reference-fix caches.

## Execution boundary

This runner executes modified bundled fixtures in short-lived Python processes.
A restrictive AST check excludes unrestricted imports, file I/O, reflection,
and unsupported calls; subprocesses have CPU/file-size limits and a five-second
wall-clock timeout. This can reject a legitimate solution outside the supported
subset, which is reported separately as `execution_rejected`.

These measures and temporary folders are **not an OS security sandbox**. There
is no support for arbitrary user repositories or untrusted external benchmark
suites here. Use container/OS isolation before expanding to those workflows.
Memory-intensive candidate expressions could still put pressure on your Mac.
The interactive app remains read-only and does not execute candidates.

## Results

Each run creates its own folder under `eval-results/`. Self-check and live runs
are separate folders. The final Terminal line prints the exact output path.

- `summary.md`: readable outcome table and review guidance.
- `summary.json`: counts, repair rate, timing, model name, Ollama/Python versions,
  prompt text, and source-file hashes.
- One JSON per case: issue, evidence actually supplied, raw model responses,
  diagnostic errors, generated diff, baseline and candidate test results.

Completed cases are saved immediately. Control+C preserves them; the summary
reports completed versus planned cases. A later run starts fresh, rather than
silently resuming or mixing results.

| Outcome | Meaning |
|---|---|
| repaired | Accepted proposed edit passes all predefined tests. |
| tests_failed | Accepted edit fails one or more tests or times out. |
| format_rejected | Edit response cannot be parsed. |
| validation_rejected | Source-match, syntax, snapshot or supported-target check fails. |
| execution_rejected | Candidate uses constructs outside the executable subset. |
| no_edit | Model explicitly declines to propose a fix. |
| output_truncated | A generation hit its configured output cap. |
| model_error | An inference stage fails or returns no usable response. |
| harness_error | Fixture/runtime setup is invalid; inspect the case error. |
| fixture_verified | Self-check only; no model accuracy measurement. |

Repair-rate denominator includes valid attempts that fail through model errors,
formatting, validation, or execution rejection. Harness-invalid cases are
explicitly excluded and counted separately. Partial-run rates cover only
completed cases. Passing finite tests does not establish universal correctness.

Explanation quality is **not automatically scored**. In each case JSON compare
`result.stages[0].content` with `context`. Note factual errors, unsupported
citations, and claims that supplied evidence is missing. The review fields start
as `not_reviewed`; they are not counted as passes. A correct repair can accompany
an inaccurate diagnosis, as our earlier experiments demonstrated.

## Validation performed on this deliverable

All six fixture baselines fail and all six reference repairs pass. Fifteen tests
pass, including actual execution of mocked reference proposals, rejection of
wrong proposals, parser behavior, HTTP errors, and summary denominator handling.
Model calls were mocked: **no live Qwen success rate has been measured here**.
Run the evaluation on your Mac to obtain it.
